# 检索层具体说明

本文件说明检索层的四层分别在做什么、为什么需要它们。
配合 `docs/RAG_PIPELINE_PLAN.md`（总方案）和 `docs/chunk具体说明.md`（切片细节）一起看。

**切片解决"知识库里有什么"，检索层解决"怎么把对的那条捞出来"。**

---

## 全景：一个问题走完四层

```
用户问："我GMAT 680够吗？"
   │
   ├─【① 向量检索】(已完成)  问题转向量 → pgvector 余弦相似度 → 取 top-N
   │      擅长：意思相近就能找到（"要花多少钱" ↔ "tuition fee"）
   │      短板：精确代号/数字容易漏（FT5005、S$74,120）
   │
   ├─【② BM25 关键词】        按词频精确匹配 → 取 top-N
   │      擅长：FT5005、GMAT、IT5001X 这类精确词
   │      短板：不懂意思（"花多少钱"匹配不到"tuition"）
   │
   ├─【③ RRF 融合】           把 ①② 两份排名合并成一份
   │      解决：两路各有所长，谁也不能单独定胜负
   │
   └─【④ Rerank 精排】        对融合后的候选做精细打分 → 取 top-5
          解决：把"看着像但答不对题"的压下去
                ↓
          交给回答 LLM 生成答案
```

**核心思想：①② 负责"广撒网、别漏"，③ 负责"合并"，④ 负责"精挑、排准"。**

---

## ① 向量检索（Dense Retrieval）— 已完成

**在干什么**：把问题也转成 1536 维向量，在 `document_chunks.embedding` 里找"坐标最近"的 chunk（余弦相似度，走 HNSW 索引）。

**为什么有用**：能按**意思**检索，不靠字面。用户问"读这个要花多少钱"，能命中写着 "tuition fee S$74,120" 的 chunk —— 一个字都不重合。

**实测短板**（来自 `scripts/test_search.py`）：
- 中文问"想做量化风险分析师"→ `role:quant_risk` 只排第 2（英文问时排第 1）→ 跨语言有损耗
- 问"NUS vs NTU"→ 不相关的 Test Scores 节因为含 "GMAT" 挤进 top3 → 表面相似

**这两个短板正是 ②④ 要补的。**

---

## ② BM25 关键词检索（Sparse Retrieval）

**在干什么**：不看意思，只看**词对不对得上**。BM25 是个经典的关键词排名算法（改进版 TF-IDF，考虑词频饱和 + 文档长度归一化），生产搜索引擎（Elasticsearch）都用它。

**为什么这个项目特别需要它**：我们的语料里全是**精确代号和数字**——
```
FT5005 / IT5001X / BMD5301     课程代码
GMAT 650 / IELTS 6.0 / GRE 320  分数
S$74,120 / S$7,412 / S$109      金额
```
这些东西**向量最容易搞混**（FT5005 和 FT5009 的向量非常接近），但 BM25 能精确命中。而且**数字和代号中英文都一样**，天然跨语言。

**实现选择：`rank_bm25` 内存版，不用 Elasticsearch**
- Anthropic cookbook 用 Elasticsearch（Docker 起服务）
- 但：本机只有 8GB 内存，ES 光 JVM 堆就要 2GB+；而我们**只有 184 个 chunk**
- 为 184 条数据起一个搜索引擎集群 = 杀鸡用牛刀
- → `rank_bm25` 把 184 条读进内存算，10 行代码、零基础设施、毫秒级

**关键细节：BM25 搜的是 `context + content`**，和 embedding 用的是同一份文本。
这样我们给 chunk 加的 context 前缀（含项目名、技能中文别名）**同时惠及向量和 BM25**
—— 这正是 cookbook 里"Contextual BM25"的做法。

---

## ③ RRF 融合（Rank Fusion）

**在干什么**：①② 各返回一份排名，同一个 chunk 在两份里名次不同，需要合并成一份最终排名。

**为什么不能简单相加分数**：向量的相似度是 0~1 的余弦值，BM25 的分数是没有上界的词频统计值 —— **两者量纲完全不同，直接相加没有意义**。

**RRF 的解法：只看名次，不看分数。**
```
score(chunk) = w_semantic × 1/(rank_semantic) + w_bm25 × 1/(rank_bm25)
```
- 在某一路排第 1 → 贡献 1/1；排第 10 → 贡献 1/10
- 名次越靠前贡献越大，且**两路可比**（都是名次的倒数）
- **两路都命中的 chunk 会得到双份加成 → 自动浮上来**

**权重**：跟随 cookbook 的默认值 **semantic 0.8 / bm25 0.2**（语义为主、关键词补充）。
这两个值可调，后续可用评估集测出最优比例。

> 严格说这是"加权倒数排名融合"，标准 RRF 公式是 `1/(k+rank)`（k 常取 60）。
> cookbook 用的是简化的 `1/rank` 加权版，效果相当，我们跟随它以便对照数据。

---

## ④ Rerank 精排（Cross-Encoder）

**在干什么**：融合后拿到一批候选（比如 top-50），用一个**更聪明但更慢**的模型逐个精细打分，选出真正最相关的 top-5。

**为什么 ①② 不够、非要再来一层**：
| | ①② 检索 | ④ Rerank |
|---|---|---|
| 怎么算 | 问题和 chunk **各自**转成向量，再比距离 | 问题和 chunk **一起**喂给模型，直接判断相关度 |
| 术语 | bi-encoder（双塔）| **cross-encoder**（交叉编码）|
| 速度 | 极快（有索引，百万级也毫秒）| 慢（每个候选都要跑一次模型）|
| 准度 | 一般 | **高**（能理解问题和文档的交互）|

所以策略是**两阶段**：
1. **①②③ 广撒网**：快，从 184 条里捞出 50 个候选（宁可多捞，别漏）
2. **④ 精挑**：慢但准，只对这 50 个精算，选出 top-5

**选型：Cohere `rerank-multilingual-v3.0`**
- ✅ 不吃内存（API 调用）—— 本机 8GB，跑不动本地 cross-encoder
- ✅ Trial key 免费，每月 1000 次调用，capstone 用不完
- ✅ 多语言版，覆盖中文提问场景
- ✅ cookbook 用的同一家，效果有对照数据

**代价**：每次查询多 ~100-200ms 延迟。对聊天场景可接受（回答 LLM 本身就要 1-3 秒）。

## 为什么值得做这四层：cookbook 的实测数据

Anthropic 在 9 个代码库、737 chunk、248 道题上的结果：

| 方法 | Pass@5 | Pass@10 | Pass@20 |
|---|---|---|---|
| 基线（纯向量）| 80.92% | 87.15% | 90.06% |
| + 上下文嵌入 | 88.12% | **92.34%** | 94.29% |
| + 混合搜索(BM25) | 86.43% | 93.21% | 94.99% |
| + 重排序 | **92.15%** | **95.26%** | **97.45%** |

**检索失败率从 12.85% 降到 4.74%（降低 47%）。**

⚠️ **但注意，这是别人的数字，不是我们的**：
- 他们的语料是代码库，我们是招生文档
- 他们的 context 是 **LLM 生成**的，我们是**模板拼**的（方案 A）
- 他们 248 道题，我们只有 50-80 道 → 分辨率更粗，小改进（如 +0.87）测不出来

**所以我们要用自己的评估集跑出自己的数字**（Step 7），而不是引用他们的。
